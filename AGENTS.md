# AGENTS.md

## Project: CPU Raytraced EggWars Diorama

This repository contains the second Computer Graphics course project: a CPU raytracer written in Rust that renders a Minecraft-inspired EggWars diorama.

This document is the authoritative engineering and design specification for AI coding agents working on the repository.

Read this file before making changes.

If an implementation choice conflicts with this document, follow this document unless the user explicitly approves a change.

Do not silently reinterpret, replace, or remove established architectural decisions.

---

# 1. Core Project Goal

Build a visually appealing raytraced diorama inspired by classic Minecraft EggWars from approximately the Minecraft 1.6–1.8 era.

The final scene represents the aftermath of an EggWars match.

The scene consists primarily of:

- four outer floating islands;
- one larger central island;
- bridges connecting or partially connecting islands;
- intact and destroyed bridges;
- intact and destroyed egg defenses;
- opened chests;
- arrows and other small environmental storytelling details;
- exposed ores;
- procedural floating-island terrain;
- lava;
- a sunset-to-night sky.

The project should deliberately demonstrate the raytracing features required by the course rubric.

This is not a general-purpose Minecraft clone.

This is not a game engine.

This is a specialized CPU raytracer optimized for this particular voxel-heavy diorama.

Every engineering decision should respect that scope.

## Diorama Interaction Model

This project is an interactive raytraced diorama, not a playable Minecraft or EggWars game.

There is no player-controlled entity inside the scene.

The user exists conceptually outside the diorama and interacts with it exclusively through the orbital camera.

The application may support:

- orbiting the camera around the diorama;
- changing camera elevation;
- zooming toward or away from the diorama;
- presentation/debug controls where useful.

The application must NOT introduce gameplay systems such as:

- a controllable player or avatar;
- first-person movement;
- walking or flying through the world;
- player collision;
- jumping;
- combat;
- inventory;
- block placement or destruction;
- EggWars gameplay mechanics.

Environmental objects such as arrows, weapons, opened chests, destroyed defenses, bridges, and missing eggs are static storytelling elements representing the aftermath of a past battle.

Do not implement player/gameplay systems unless the project requirements are explicitly changed.

# 2. Non-Negotiable Constraints

These constraints are absolute unless the user explicitly changes them.

## 2.1 Rust

The project is written in Rust.

Prefer stable Rust.

Avoid nightly-only features unless explicitly approved.

## 2.2 External Libraries

Third-party libraries are forbidden by default.

### Temporary Explicit Exception: Raylib

Until the course restriction is clarified, `raylib` is the only explicitly authorized third-party dependency.

Raylib may be used exclusively as a thin platform/presentation layer for:

- creating and managing the application window;
- reading keyboard input;
- reading mouse input;
- obtaining frame timing;
- presenting the CPU-generated framebuffer on screen;
- minimal application lifecycle functionality required for the above.

Raylib must NOT be used for:

- ray generation;
- ray-object intersection;
- raycasting or raytracing;
- rendering 3D scene geometry;
- drawing the diorama using Raylib 3D primitives;
- lighting;
- shadows;
- materials;
- textures used by the raytracer;
- reflection;
- refraction;
- normal mapping;
- emission calculations;
- procedural generation;
- spatial acceleration;
- voxel traversal;
- any computation that belongs to the raytracer itself.

The architectural boundary must remain:

`Scene + Camera -> CPU Raytracer -> CPU Framebuffer -> Presentation Layer -> Raylib -> Window`

The framebuffer presented by Raylib must have been generated by our CPU renderer.

### Isolation Requirement

Core raytracing modules must not depend on Raylib types.

In particular, modules such as:

- `math`;
- `ray`;
- `geometry`;
- `camera`;
- `scene`;
- core `render`;

must remain usable independently from Raylib.

Raylib-specific code should live at the application/presentation boundary.

Do not expose Raylib vectors, colors, textures, cameras, rays, models, or other Raylib-specific types through core renderer APIs.

If Raylib becomes forbidden by the course requirements, it must be possible to replace the presentation/input layer without rewriting the raytracer.

### Dependency Policy

The presence of Raylib does NOT authorize adding other third-party crates.

Do not add any additional dependency to `Cargo.toml` without explicit user approval.

If functionality can reasonably be implemented with the Rust standard library and project code, implement it locally.

Raylib itself should not be added until the project actually reaches the presentation/window

GPU acceleration is forbidden.

Do not introduce:

- CUDA;
- OpenCL;
- Vulkan compute;
- Metal compute;
- GPU shaders used for rendering;
- WebGPU;
- OpenGL-based raytracing;
- any equivalent GPU acceleration.

The raytracing work must execute on the CPU.

## 2.4 Optimization Is a First-Class Requirement

Performance is part of the project's design, not an afterthought.

Avoid unnecessary:

- heap allocations;
- cloning;
- dynamic dispatch;
- temporary vectors;
- repeated calculations;
- per-ray allocations;
- per-pixel allocations;
- recalculation of static scene data.

Prefer simple contiguous data structures where practical.

Optimize based on measurements when possible.

Do not sacrifice correctness for speculative micro-optimizations.

Algorithmic improvements are preferred over clever low-level tricks.

# 3. Fundamental Rendering Philosophy

The scene is voxel-heavy.

Exploit this aggressively.

## 3.1 AABB-First Geometry

Minecraft blocks and most decorative geometry should be represented using axis-aligned bounding boxes whenever practical.

Prefer AABBs for:

- terrain blocks;
- bridges;
- structures;
- chest components;
- arrows;
- swords;
- egg sculptures;
- decorative objects.

Do not introduce arbitrary triangle meshes merely because they are conventional in raytracers.

Do not introduce arbitrary rotated boxes unless there is a strong visual reason and the user approves the additional complexity.

Pixelated approximations are intentional and appropriate for the art direction.

---

## 3.2 Avoid Unnecessary Geometry

Do not create geometry that cannot contribute to the rendered image.

Interior blocks completely surrounded by opaque blocks should eventually be eligible for culling or exclusion from expensive intersection work.

Procedural terrain may maintain logical occupancy separately from render-visible geometry.

---

## 3.3 Future Spatial Traversal

The intended acceleration architecture is a voxel grid with 3D DDA traversal.

Do not prematurely implement this during Phase 1.

However, early architecture must avoid making 3D DDA unnecessarily difficult to introduce later.

Do not design the renderer around permanent brute-force intersection with every object in the scene.

---

# 4. Coordinate and Math Conventions

The renderer is genuinely 3D.

Do not copy the old Doom project's 2D world assumptions.

Create explicit 3D mathematical types.

At minimum the core will require:

- `Vec3`;
- `Ray`;
- camera vectors;
- AABB bounds.

Use a single consistent coordinate convention throughout the project.

Document the chosen convention in the math/camera code.

Avoid hidden coordinate-system conversions.

Vectors and rays should use `f32` unless profiling or numerical evidence demonstrates a reason to change.

Numerical code should defend against:

- NaN;
- infinity;
- division by values near zero;
- invalid normalization;
- zero-length direction vectors.

Use clearly named epsilon constants where necessary.

---

# 5. Camera

The final diorama uses an orbital camera.

The camera should orbit around a target point near the center of the arena.

The camera must support:

- horizontal orbit;
- appropriate 3D viewing orientation;
- zooming toward the target;
- zooming away from the target.

The camera should be represented using meaningful parameters such as:

- target;
- orbit angle / yaw;
- elevation / pitch where appropriate;
- radius / distance;
- vertical field of view;
- aspect ratio.

Do not model the final camera as a Doom-style 2D player.

Camera movement and scene geometry are separate concerns.

The eventual controls/presentation mechanism is not finalized.

Keep camera logic independent from input/windowing code.

---

# 6. Framebuffer

Rendering must target a CPU-owned framebuffer.

The renderer must not depend directly on a specific windowing API.

Conceptually:

`Scene + Camera -> Renderer -> Framebuffer`

The framebuffer should own or manage pixel data in a simple contiguous representation.

The presentation layer may later display this framebuffer or write it to an image format.

During early development, writing a simple image format implemented locally is acceptable.

Prefer a trivial format such as PPM for initial validation if needed.

Do not add an image crate.

---

# 7. Ray and AABB Intersection

Phase 1 uses ray-versus-AABB intersection as the fundamental geometry operation.

Use a robust slab-based intersection algorithm.

The implementation should correctly handle:

- rays approaching from positive directions;
- rays approaching from negative directions;
- rays starting inside an AABB;
- rays parallel or nearly parallel to a slab;
- misses;
- hits;
- finite distance constraints.

Intersection results should eventually provide enough information for shading, including at least:

- hit distance;
- hit position;
- surface normal;
- object/material identity where appropriate.

Avoid unnecessary allocation in intersection functions.

Intersection functions should be testable independently from rendering.

---

# 8. Materials and Block Types Are Different Concepts

Do not conflate block identity with optical behavior.

A block type describes what a voxel represents visually.

Examples may eventually include:

- grass;
- dirt;
- stone;
- cobblestone;
- coal ore;
- iron ore;
- gold ore;
- diamond ore;
- obsidian;
- glass;
- lava;
- wood;
- chest components;
- bridge blocks.

A material describes how a surface interacts with light.

The final project must intentionally demonstrate at least five distinct rubric-counting materials.

The planned primary materials are:

1. grass/dirt;
2. cobblestone/stone;
3. obsidian;
4. glass;
5. lava.

Each rubric-counting material must have:

- its own texture;
- albedo parameters;
- specular parameters;
- transparency parameters;
- reflectivity parameters.

Additional block textures do not necessarily require new optical models.

Do not implement the material system during Phase 1 beyond what is minimally required to distinguish basic test objects.

# 10. Procedural Terrain

Procedural terrain is a required major feature.

Each outer island should be based on at least a 16x16 horizontal grid.

The chosen generation strategy is:

- deterministic procedural generation;
- configurable seed;
- radial mask;
- noise/variation implemented locally;
- layered terrain composition.

The exact algorithm may evolve during the terrain phase, but the radial-mask design is established.

Conceptually:

- surface: grass;
- shallow subsurface: dirt;
- deeper volume: stone;
- selected stone positions: ores.

Possible ores include:

- coal;
- iron;
- gold;
- diamond.

Ore distribution should favor visible or potentially visible locations rather than wasting geometry deep inside permanently hidden terrain.

The underside of floating islands should be irregular and taper toward the void.

The top must remain usable for EggWars structures.

---

# 11. Deterministic Seed

Procedural generation must be reproducible.

A configurable seed is mandatory.

The same seed and configuration must produce the same terrain.

Do not depend on external randomness crates.

Implement any required deterministic PRNG/hash/noise functionality locally.

The project should eventually allow experimenting with different seeds while preserving a chosen seed for the final recorded scene.

# 12. Scene Art Direction

The scene represents the aftermath of a completed or nearly completed EggWars battle.

Avoid four perfectly identical pristine islands.

Environmental storytelling should include a deliberate mixture of:

- intact eggs;
- destroyed eggs;
- intact defenses;
- damaged defenses;
- opened chests;
- completed bridges;
- partially destroyed bridges;
- missing bridge sections;
- arrows;
- abandoned equipment;
- exposed ores;
- damaged terrain;
- lava.

These elements should remain computationally inexpensive.

Prefer voxel/AABB constructions over complex geometry.

The central island is the visual focal point.

Bridges should help guide the viewer's eye toward the central island.

Lighting should reinforce this composition.

---

# 13. Lighting Direction

The final scene uses a sunset/night composition.

The intended broad lighting hierarchy is:

1. sky/environment illumination;
2. remaining directional sunset light;
3. emissive lava and other justified emissive elements.

The environment should contain enough darkness for emissive materials to be visually meaningful.

Do not make the entire scene so bright that lava emission becomes irrelevant.

Do not make the scene so dark that textures and geometry become unreadable.

---

# 14. Parallel Rendering

Parallel rendering is required.

The chosen strategy is dynamic tile-based CPU multithreading.

Do not replace this with static horizontal stripes unless explicitly approved.

The intended design is approximately:

- split framebuffer into tiles;
- maintain render jobs for tiles;
- worker threads acquire available jobs;
- each worker renders its tile;
- continue until all tiles are complete.

Use:

`std::thread`

and other standard-library synchronization primitives where needed.

Eventually determine worker count using available CPU parallelism.

Tile size must not be treated as unquestionable.

Candidate sizes such as:

- 8x8;
- 16x16;
- 32x32;

should eventually be benchmarked.

The final README should be able to explain why the selected configuration was chosen.

Do not implement parallel rendering until its designated performance phase unless explicitly requested earlier.

Each meaningful implementation block should receive its own commit.

Do not bundle unrelated changes into one commit.

A feature implementation and an unrelated refactor should normally be separate commits.

Tests directly belonging to a feature may be committed with that feature when appropriate.

Do not create meaningless commits solely to increase commit count.

- `changes`;
- `fix`;
- `stuff`;
- `update`;
- `final`;

- `working`;

Before committing:

2. verify no unrelated files are included;

# 30. Definition of Done for Any Change

A change is not complete merely because code was written.

Before considering a requested implementation finished:

- the implementation matches the requested phase;
- established architecture has not been silently violated;
- no third-party dependency was introduced;
- CPU-only constraints remain intact;
- relevant tests exist and pass;
- `cargo fmt --check` passes;
- `cargo test` passes;
- `cargo check` passes;
- relevant release compilation succeeds when appropriate;
- unnecessary allocations were avoided in obvious hot paths;
- the diff contains no unrelated modifications;
- the change has an appropriate Conventional Commit;
- existing working behavior remains intact.

If any item cannot be satisfied, report it clearly instead of pretending the task is complete.
